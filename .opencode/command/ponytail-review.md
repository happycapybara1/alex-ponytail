---
description: "Review the current changes: bugs, security, load, tests, speed, bloat"
---

Review the current code changes like the senior developer who gets paged when they break. Review what the user names (uncommitted or staged changes, a branch, a PR, files); nothing named: the uncommitted changes, or the last commit if there are none. First read the code around the change: callers of every changed function, the functions it calls, the tests, the README; a change can break code it does not touch, so when a signature, return value or behavior changes, grep every caller. Find the expected load (one person or many users and processes) and judge scale against it. Look for, in this order: bugs (wrong result, crash, missed edge case, a caller broken by the change, a fix in one caller while the shared function stays broken), risk (security holes, data loss), scale (check-then-write races, the same work in every process, memory that only grows, a query per item, O(n^2) on big input), risky logic without a test, slow code (big = problem, small = suggestion), lean (dead code, a helper the repo already has, the standard library or platform instead of custom code or a new dependency, abstractions with one implementation, near-copies to merge, a function doing unrelated jobs to split, never split by line count). Every finding needs a concrete case (this input leads to this wrong result); re-read the lines to confirm it. A shortcut: (or older ponytail:) comment that names its limit is a decision, not a finding. Propose the smallest fix, prefer deleting code, never add layers. No style taste, no vague worries. Very simple English, explain technical terms. First line: 'Verdict: Ship.' or 'Verdict: fix 1 and 3 first.' Then 'What this change does:' in two or three sentences and the load you assumed. Then numbered findings grouped Must fix / Should fix / Nice to have; each: a bold title with file:lines, then four bullets: What this is, Problem, Fix, If we skip it (one or two short sentences each). End with 'Lean: -N lines possible.' when lean findings exist, and 'Not checked:' if something mattered and you could not check it. Change no code.
